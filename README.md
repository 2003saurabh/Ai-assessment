# TechNova AI Chatbot — Dual-Mode Agentic RAG

A production-grade chatbot that answers questions about TechNova Inc. using two distinct retrieval strategies: **vector-based document search (RAG)** and **text-to-SQL** over structured order data — routed by an LLM agent.

### Request Flow

1. User sends a question via the Next.js frontend.
2. The frontend immediately shows a "Thinking..." status indicator.
3. A **Router Agent** (Claude Haiku) classifies the question AND generates SQL if needed — in a single fast call (~0.5s).
4. Based on the route:
   - **RAG**: Embeds the query via Bedrock Titan → searches pgvector (HNSW index) for top-k chunks → streams answer with citations.
   - **SQL**: Executes the pre-generated query against PostgreSQL → streams summarized results.
   - **Both**: Runs RAG retrieval and SQL execution **in parallel** (`asyncio.gather`) → streams combined answer.
   - **Fallback**: Returns a safe "I don't have that information" response immediately.
5. The final answer is generated by Claude Sonnet and streamed token-by-token to the frontend.

## Key Optimizations

| Optimization | Impact |
|-------------|--------|
| **Dual-model setup** (Haiku for routing, Sonnet for answers) | ~1s faster per request, lower cost for routing |
| **Merged route + SQL generation** (single LLM call) | Eliminates 1 full LLM round-trip (~1.5s saved) |
| **Streaming status indicators** | User sees "Thinking...", "Querying database..." immediately — no blank wait |
| **Parallel execution** (both route) | RAG + SQL run concurrently instead of sequentially |
| **pgvector with HNSW index** | Sub-10ms vector search, scales to millions of chunks |

**Before:** SQL route took ~4.5s (route → sql_gen → execute → answer)
**After:** SQL route takes ~2.0s (route+sql via Haiku → execute → answer via Sonnet)

## Model & Technology Choices

| Component | Choice | Reasoning |
|-----------|--------|-----------|
| **LLM (Answers)** | Claude 3.5 Sonnet (Bedrock) | Strong reasoning, excellent instruction following, high-quality answers |
| **LLM (Routing)** | Claude 3.5 Haiku (Bedrock) | 3-5x faster than Sonnet, sufficient for classification + SQL generation |
| **Embeddings** | Bedrock Titan Embed Text v2 | 1024-dim vectors, managed service, no local model overhead |
| **Vector Store** | pgvector (PostgreSQL extension) | HNSW index for fast search, same DB for vectors + structured data, scales to millions |
| **Database** | PostgreSQL 16 | Production-grade, separate container, persistent storage, supports pgvector |

## Routing Decision

The agent uses a **single Haiku call** that both classifies the question AND generates SQL when needed. The combined prompt includes the database schema so routing and SQL generation happen atomically.

- **Document questions** (policies, product info, how-to) → `rag`
- **Data questions** (revenue, counts, order status) → `sql` + SQL query
- **Mixed questions** (policy + data cross-reference) → `both` + SQL query
- **Unrelated questions** → `fallback`

This approach was chosen over separate routing + SQL calls because:
1. Eliminates a full LLM round-trip (~1.5s saved).
2. The model already understands the intent when routing — generating SQL at the same time is trivial.
3. Haiku handles both tasks in ~0.3-0.5s total.

## Setup & Running

### Prerequisites
- Docker & Docker Compose
- AWS credentials with Bedrock access (Claude Sonnet + Haiku + Titan Embeddings enabled)

### Quick Start

```bash
# Clone the repository
git clone https://github.com/2003saurabh/Ai-assessment.git
cd Ai-assessment

# Copy environment file and add your AWS credentials
cp backend/.env.example backend/.env
# Edit .env with your AWS credentials

# Run with Docker Compose
docker-compose up --build
```

The app will be available at:
- Frontend: http://localhost:3000
- Backend API: http://localhost:8000
- API Docs: http://localhost:8000/docs
- PostgreSQL: localhost:5432

### Local Development (without Docker)

**Prerequisites:** PostgreSQL with pgvector extension installed locally.

**Backend:**
```bash
cd backend
pip install -r requirements.txt
cp .env.example .env  # Add your credentials + DATABASE_URL
uvicorn app.main:app --reload --port 8000
```

**Frontend:**
```bash
cd frontend
npm install
npm run dev
```

## Streaming Protocol

The backend streams a mix of JSON control messages and raw text tokens:

```
{"type":"status","message":"Thinking..."}\n              ← status (shown as spinner)
{"type":"status","message":"Querying database..."}\n     ← status update
{"type":"metadata","tool_used":"sql","sql_query":"..."}\n ← metadata (tool badge)
There are currently **5** pending orders.                 ← answer tokens (streamed)
```

The frontend parses lines starting with `{` as JSON (status/metadata) and everything else as content.

## Known Limitations

1. **Single-turn routing**: The router classifies each message independently — no conversation history.
2. **SQL injection surface**: While only SELECT queries are allowed, the LLM-generated SQL is executed directly. Production should add query sanitization.
3. **No conversation memory**: Each question is processed independently. Follow-up questions like "what about last week?" won't resolve context.
4. **Cold start**: First request embeds all documents into pgvector (one-time, ~30-60s for 3 documents). Subsequent requests are fast.
5. **Fixed date**: The system treats the current date as June 15, 2026, as specified in the assessment requirements.
